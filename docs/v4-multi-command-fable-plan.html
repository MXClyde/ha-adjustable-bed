Adjustable Bed v4 Multi-Command Architecture: Fable Plan

Independent architecture plan derived from the released v4.0.0b3 tree (commit 998b52c). Design only, no implementation. All file:line anchors were checked against that commit. Every protocol without authoritative concurrency evidence uses strict serial execution with queue-not-cancel semantics.

TLDR

In b3, every per-device coordinator has exactly one command lock and one global cancel token. Any motion command bumps _cancel_counter and sets _cancel_command coordinator.py:4292-4293, so a legs command kills a running back seek; and the 60-second seek loop holds _command_lock for its whole lifetime coordinator.py:4931, const.py:2247, so even a non-cancelling command (a light toggle uses cancel_running=False light.py:277) waits up to a minute. The pair layer repeats the pattern one level up: _pair_command_lock serializes even non-overlapping side commands paired_coordinator.py:296.

The fix is a per-physical-device command scheduler built from scoped tickets, a wire gate, and an optional motion-intent registry. Each ticket declares resource scope, lifetime, physical completion policy, priority, and a private cancel token. Cancellation becomes scope-intersection instead of global. A monotonic STOP generation prevents work admitted during a stop race from starting afterward. The BLE wire remains strictly serialized per device at the existing _ble_lock boundary.

The default execution model for every protocol is serial with queue-not-cancel semantics: a request on a different axis queues after the active ticket, never cancelling or interleaving with it. That fixes the reported bug without promising simultaneous movement. Interleaved bursts, combined multi-axis frames, and direct-target coexistence each require protocol-specific authoritative evidence. Separate-address concurrent pairs are the evidence-free exception because two physical BLE links can overlap while each link still sees serial traffic, subject to v4's existing connection mode const.py:149-158. The pair parent becomes a router: single-side pass-through, linked two-phase reservation for both, and the unchanged sequential lane for one-link pairs.

2. Defect enumeration, and what the serial default does about each

  1. Cross-axis cancellation. A back seek's loop breaks on the global event coordinator.py:5091. Any cover open/close (cover.py:408), motor button (cancel_movement=True, button.py:534), or new seek on any other axis sets it. The reported bug. Fixed for all protocols by queue-not-cancel: disjoint scopes never touch each other's tokens.
  2. Cross-axis blocking. A non-cancelling command queues behind the seek's 60-second lock hold: light writes (light.py:277), save_preset (cancel_running=False, services.py:504), background position reads (coordinator.py:4558). Only partially addressed by default. Queued waits remain (they are the safe behavior), but they become bounded by the active ticket's own deadline, visible in diagnostics, and warned about in the log. Reads that b3 already performs mid-motion move to the QUERY lane and stop queueing. Full unblocking of aux writes during motion requires per-protocol interleave evidence (section 5).
  3. Cross-child blocking in a pair. Concurrent-mode children are independent BLE devices, yet a right-side command waits for a left-only seek to finish because everything takes _pair_command_lock paired_coordinator.py:296. async_run_child_operation (used by set_position) rides the same lock, so left and right seeks cannot overlap even across two physical links. Fixed for separate-address pairs in concurrent connection mode: two links, two schedulers, no protocol sees new traffic on its own link.
  4. Over-broad hold release. Releasing a held button-backed motor calls the bed-wide stop (hold.ts:110-123 via the stop button, button.py:855 async_stop_command), which cancels every axis, including an unrelated seek. Fixed by ticket-scoped release stop (section 6.4): a queued-never-started hold is dropped with zero wire writes; only an actually-running hold gets a stop write.
  5. Global preemption races. The preemptible wait races an operation against the one shared event coordinator.py:4237-4275; any command's cancel aborts any other preemptible operation, including queries. Fixed by per-ticket tokens.
  6. Global mutable pulse settings. timed_move temporarily rewrites coordinator._motor_pulse_count "safe because we're inside the command lock" services.py:874-885. Safe only while the lock is global; the redesign threads overrides through the ticket instead. Fixed.

3. Design principles

  • One wire, one owner. BLE serialization stays per physical device at the GATT-operation level. No design element ever issues concurrent GATT operations on one link.
  • Cancellation is scoped, never global. A command may only cancel what it conflicts with. STOP is the only actor that may cancel everything, and it always completes.
  • Declared, never guessed. This repository forbids guessing or extrapolating protocol timing and behavior. Any wire pattern a protocol has not been proven to receive today is off by default: interleaved cross-axis bursts, combined multi-axis frames, concurrent direct targets, and simultaneous streaming each require a per-protocol declaration backed by written authoritative evidence (fresh APK decompile finding, vendor documentation, or a dated bench test). There is no "safe by construction" tier for new wire timing.
  • Queueing is the only evidence-free improvement on one link. Running command B after command A finishes produces bytes the bed already receives when a user issues B after A. Reordering in time needs no protocol knowledge; changing the wire pattern does. Hence the universal default: different-axis requests queue, never cancel, never interleave.
  • Link-level concurrency is not protocol concurrency. Two separate BLE devices in an already-supported concurrent pair mode may run at once because each device still sees strictly serial traffic on its own link. This is the one form of simultaneity that requires no protocol evidence.
  • Unannotated equals b3. Every existing call site, unmodified, must behave byte-identically on the wire. Improvements are opt-in per call site (scope annotation) and, where evidence is required, per protocol (concurrency declaration).
  • Children own scheduling; the parent owns routing. The scheduler lives where the link lives. The pair parent holds no BleakClient (b3 invariant) and therefore holds no scheduler, only admission routing and the both barrier.

4. Core design: the per-child command scheduler

4.1 Command scopes and tickets

Every operation the coordinator runs is admitted as a ticket with a typed scope:

  • MOTION with an axis set, e.g. {"back"}. Covers, motor buttons, seeks, timed moves.
  • PRESET, exclusive over all motion axes of the child (recalls and streaming presets drive several motors; preset_flat, preset_memory, streaming _preset_with_stop, base.py:698-719).
  • AUX with a channel, e.g. lights, massage, firmness. Conflicts only with the same channel.
  • QUERY: position reads, state refreshes, hydration, passive reconciliation. Conflicts with nothing; ordering is provided by the wire gate alone. The QUERY lane introduces no new mid-motion traffic: only reads b3 already performs during motion (feedback-protocol polling, coordinator.py:5034-5040) run while a motion ticket is active; on other protocols queries simply queue as today.
  • STOP: never conflicts, never queues, always runs (priority lane).

Scope answers what the operation owns. Two separate fields answer questions a lock cannot:

  • Lifetime: DURABLE intents (position targets, presets, automation commands) stay queued until completion or explicit replacement. RELEASE_BOUND intents (pointer or keyboard holds) live only while their input owner remains active. Releasing a queued hold drops it with zero BLE traffic; it never replays after the user lets go.
  • Completion: OPERATION_RETURN, POSITION_FEEDBACK, PROTOCOL_NOTIFICATION, or DEADLINE. A direct-target write returning is not proof the motor stopped. Where coexistence is unverified, its ticket keeps a motion lease until the declared completion signal or conservative deadline.

Conflict rule: MOTION vs MOTION conflict iff axis sets intersect; anything vs an exclusive PRESET conflicts if it is MOTION or PRESET; AUX conflicts with same-channel AUX. Admission with replace_conflicting=True (the default for motion, matching b3's cancel_running=True) sets the cancel token of every conflicting active or queued ticket, then waits for them to drain. A non-conflicting ticket is queued behind the active one and starts when the scheduler reaches it; it never touches the active ticket's token. A queued ticket whose own token was set before it starts is dropped, which is b3's counter check coordinator.py:4300 made scope-local.

Each ticket owns a private asyncio.Event. The scheduler sets a ContextVar while running a ticket's coroutine, and coordinator.cancel_command coordinator.py:1631 resolves through it. Since _write_gatt_with_retry already falls back to that property base.py:516, existing controller loops become scoped without a mass edit. This is a migration bridge, not a forever-hidden API: new scheduler-aware controller hooks receive the ticket token explicitly, and any controller-created background task must be audited so copied context cannot outlive its ticket.

4.2 The wire gate

The wire gate replaces _command_lock at the same call sites. Differences from a plain lock:

  • STOP priority and generation. A pending STOP acquires ahead of the FIFO. Before waiting, it increments a monotonic stop generation and invalidates every covered queued ticket. Admission snapshots that generation and rechecks it before activation, so a movement racing STOP cannot start afterward. b3's "stop waits for the in-flight GATT write" property remains because a step never releases mid-write.
  • Per-step acquisition for long operations. Short commands (one movement burst including its internal repeats, one aux write, one preset stream) hold the gate for their whole body, exactly like b3. Long operations (the seek loop) acquire per step and release at yield points. Under the serial default those yield points serve exactly three things: STOP responsiveness, same-axis replacement, and the QUERY lane. They do not admit other-axis motion or aux tickets; those stay queued until the long operation's ticket completes. Only a protocol with a declared, evidence-backed interleave_bursts profile (section 5) admits queued non-conflicting tickets at yield points. A step is atomic: one burst or one read; nothing ever splits a burst.
  • Idle callback. The gate/scheduler reports when the last ticket completes, which is where disconnect-after-command and the idle timer re-arm move to (section 9).

4.3 The motion intent registry (declared combined-frame protocols only)

Protocols whose frames are proven to encode the whole desired motion state (a button bitmask) do not need interleaving: the correct wire behavior when back and legs are both commanded is one frame stream with both bits set. For those, motion tickets do not write directly. They register an intent (axis, direction or target) and a single FrameStreamer task, owner of the gate while streaming, composes union frames via a new controller hook and emits them at protocol cadence. Removing the last intent emits the protocol's release/stop and ends the stream. A ticket's cancel removes its intent; STOP clears the registry and sends stop_all. With exactly one intent, the composed frame must be byte-identical to today's single-axis frame (regression-gated, section 14). This machinery is inert unless a bed carries a COMBINED_FRAME declaration with evidence; undeclared beds, including current combined-frame candidates, run the plain serial queue.

Why burst interleaving is not assumed safe. Inserting one bounded other-axis burst between seek steps may resemble two sequential button presses, but that analogy extrapolates timing, which this repository forbids. Human presses arrive with human-scale gaps; a scheduler could alternate motor codes at sub-second cadence inside what firmware treats as one continuous session. A dead-man state machine keyed on the last-seen motor code could halt the first motor, treat alternation as a stop, or fault. Whether stall re-issue coordinator.py:5214-5229 recovers is itself an untested timing assumption. Interleaving is therefore a per-protocol capability to prove, not a default. The universal default is queue-not-cancel.

6.4 STOP taxonomy

  1. Ticket-scoped release stop (new): the implicit stop issued when a held motor is released. Semantics: drop any queued ticket intersecting the held axis without writing anything to the wire (a command that never started needs no stop); if the intersecting ticket is active, cancel it and run the b3 bed-wide stop write path. Under the serial default this is safe without protocol knowledge: at most one motion ticket is active per device, so the stop write can only ever stop the motion the user just released. If the active ticket does not intersect the released axis (back seek active, legs hold released before its ticket started), nothing is written and the seek continues. This alone removes defect 4 on every protocol. Known b3-parity limitation: on DIRECT_TARGET beds, firmware-autonomous motion from an already-completed write is still stopped bed-wide, exactly as b3 does today; narrowing that requires per-axis stop opcodes declared with evidence (phase M3), because writing a single-axis stop while another axis's firmware seek runs is itself an unverified pattern.
  2. Child stop (stop_all): b3's contract, unchanged, plus priority lane and queue drain.
  3. Pair stop (side or both): parent fans out via _stop_children, gather with per-side error capture, never skips a side paired_coordinator.py:511-548. Unchanged, now also drains that side's scheduler queue.
  4. Emergency stop = pair stop on both sides. No separate mechanism; it is the same path exercised with everything active, which is what the tests simulate.

The visible per-side and per-bed Stop buttons keep bed-wide semantics (safety: a user hammering Stop means everything). Only the implicit stop on hold release narrows to the released ticket, which is precisely the case that causes the reported bug (release legs, kill back seek).

7. Pair layer: routing, barrier, sequential lane

7.1 Concurrent mode (separate-address two-device pairs)

This is the one concurrency improvement that needs no protocol evidence: two children with distinct BLE addresses are two physical links, and in the existing v4 concurrent connection mode (PAIR_CONNECTION_MODE_CONCURRENT, or auto resolving to it, const.py:149-158) b3 already holds both links open at once. Each link continues to see strictly serial traffic from its own scheduler, so no protocol receives any new wire pattern.

  • Single-side command: pass-through. The PairedSideProxy keeps routing writes through the parent (b3 shape), but for a single-side target in concurrent mode the parent forwards straight to that child's scheduler without any pair-wide lock. A left seek and a right burst now overlap because they touch two physical links and two schedulers. This deletes the "waits its turn" comment at paired_coordinator.py:285-296 for the disjoint case. Within each child, the serial queue-not-cancel default of section 5 still governs that child's own axes.
  • Both-command: linked two-phase barrier. The router creates one reservation per distinct child operation_identity and acquires reservations in deterministic physical-identity order. A reservation owns queue position but cannot run controller code. Only after every child reports READY does the router atomically activate the linked group and enter b3's fan-out. If any reservation is cancelled or fails, all release with zero movement. This closes an asymmetry in a simple left-then-right lock acquisition, where left could begin while right was still queued. After activation, FIRST_EXCEPTION, stop-the-other, merged stop errors, and task cleanup remain unchanged paired_coordinator.py:336-371.
  • Reservation fairness. A ready reservation may temporarily block new work on an idle child while the other child drains a conflicting ticket. It has the active ticket's bounded deadline, exposes RESERVING and blocker identity in diagnostics, and yields to STOP. It never cancels disjoint work merely to synchronize a group.
  • Side command conflicting with an active both-command: keep b3's rule paired_coordinator.py:280-289: preempt the whole both-command on both sides, never half of it, so the sides cannot desync. Implemented by linking the two barrier tickets: cancelling either cancels both.

7.2 Sequential mode (Octo)

The one-link-at-a-time constraint makes cross-child coexistence physically impossible, so the sequential path keeps b3's total order: the whole pair is one lane, the connect/op/disconnect cycle with mid-cycle cancel re-checks stays as written paired_coordinator.py:373-478. Two-phase child reservation does not apply because the connection lane itself is the reservation. Within the connected side, a disjoint command queues rather than cancelling active work. Octo gets no interleaving without evidence. Its reactive PIN push and keepalive hooks remain connection lifecycle outside the command gate coordinator.py:3001, 3269-3276.

7.3 Single-address pairs

One physical device, one link, one scheduler, so the separate-address concurrency of 7.1 does not apply here. The left/right/native-both views (SingleAddressSideCoordinator, paired_coordinator.py:656) map onto the scope machinery by prefixing axes with the side: a left back seek is MOTION {"left:back"}, a right back burst is MOTION {"right:back"}. Disjoint scopes mean queue-not-cancel: a right command no longer kills a left seek, but it runs after it, because sending one device interleaved left/right codes is exactly the unverified pattern section 5 gates. A protocol whose app is proven to drive both sides at once may declare it (these are natural COMBINED_FRAME or interleave candidates). Native-both commands (the protocol's own both-sides opcode) scope {"left:back","right:back"} and are unchanged single writes. The SideBoundController ContextVar binding beds/base.py:38-83 is untouched. The serialized non-native both (Sleep Number left-then-right, paired_coordinator.py:899-933) becomes one exclusive-per-targeted-axes ticket so its two halves cannot be split by preemption, preserving b3's stop-the-other on failure.

7.4 Frontend

hold.ts keeps its awaited pulse loop, but the backend request is explicitly RELEASE_BOUND. The release path (stopBed, hold.ts:110-123) releases that ticket: queued pulses disappear with zero wire traffic; an active pulse follows its proven cleanup path. The visible Stop button remains bed-wide. Multi-hold UI stays disabled until the resolved profile can make observable progress on both resources; SERIAL beds must not imply simultaneous motion.

The card's b3 synchronization path builds several set_position calls and runs them through settleSequentially. That makes the browser own ordering and gives the backend no atomic preflight or group identity. Replace it with one additive composite service whose targets are all DURABLE. The service validates the complete plan, resolves shared operation_identity values, and submits one linked group. Existing set_position remains a one-target compatibility wrapper.

adjustable_bed.set_positions
device_id: paired-bed
targets:
  - { side: right, motor: back, position: 42 }
  - { side: right, motor: legs, position: 18 }

# One all-target preflight and one group result.
# SERIAL devices execute in order; capable profiles may overlap safely.
Do not make the browser a scheduler. The card may render QUEUED, RUNNING, and group failure from backend state. It never fans out a combined command, guesses whether a motor is moving, or retries a released hold.

8. Position orchestration

8.1 The seek loop, restructured

The b3 loop coordinator.py:4901-5257 keeps its logic (tolerance, overshoot reversal, stall re-issue, chaining, timeout, guaranteed final stop). Structural changes:

  • Admitted as a MOTION {axis} ticket; every cancel check reads the ticket token instead of the global event (coordinator.py:5091, 5163, 5184 equivalents). The overshoot-reversal "clear cancel to allow reversal" dance coordinator.py:5168 simplifies: reversal is the same ticket, nothing external set its token, nothing to clear; a genuinely new stop or same-axis command set the token and the reversal correctly aborts.
  • Yield points: the gate is held only across (burst) and (read) steps; the position_check_interval sleep and the stall-wait windows release it. Under the serial default the only things that run there are STOP, same-axis replacement, and QUERY-lane reads; queued other-axis or aux tickets wait for the ticket to finish. On a declared DEAD_MAN_INTERLEAVE bed, queued non-conflicting bursts also run there.
  • Interleaved refreshes: the mid-seek position reads stay inside the seek's step (a read is one step), so feedback pacing is unchanged.
  • DIRECT_TARGET beds: b3 writes the target and returns immediately coordinator.py:5028-5039. Under the scoped model without coexistence evidence, the write is one step but the ticket then tracks firmware motion via the existing feedback stream until the position is within tolerance or the seek timeout elapses, holding the axis scope (not the gate) so a different-axis request queues behind real motion instead of racing unverified firmware. With per-bed coexistence evidence (M3), the ticket completes at write time and per-axis targets parallelize.
  • Declared combined-frame beds: issue_seek_step registers/updates a motion intent instead of writing, and the shared streamer carries it, merging with any other active axis.
  • Timeout unchanged: 60 s wall clock per ticket const.py:2247. Under the serial default nothing interleaves into a seek, so no runnable-time accounting is needed; a declared-interleave bed counts only time the ticket was runnable, hard-capped at 2x wall clock.

8.2 Fairness

  • Gate and queue waiters are FIFO within a priority class: STOP, then MOTION/PRESET/AUX, then QUERY. On declared-interleave beds, a long operation re-acquiring at a yield point goes to the back of its class so a queued burst gets the next slot.
  • Queued waits are bounded and visible, not failed. A queued ticket waits at most the active ticket's own deadline (the 60 s seek timeout is the worst case, the same implicit bound b3 has). It is never silently infinite: after 15 s in QUEUED the scheduler logs a warning naming the blocking ticket, and diagnostics expose queue age (section 12). No arbitrary admission-failure deadline: turning a safe wait into an error would punish the serial default this design mandates. STOP never queues at all.
  • Same-scope coalescing. A newly queued motion ticket replaces an earlier queued (not yet started) ticket with an identical scope. Hold pulses arriving during a seek collapse to at most one pending ticket per axis instead of piling up a pulse backlog that would replay after the seek.
  • Per-command pulse overrides (timed_move) move from mutating coordinator fields to a ticket-carried override consumed by motor_pulse_settings() via the same ContextVar, removing defect 6.

9. Lifecycle: disconnects, setup, unload, availability

  • Disconnect ownership. disconnect-after-command and idle-timer re-arm currently run in each operation's finalizer coordinator.py:4197-4227; with a queue of tickets they move to the scheduler's idle transition (active + queued count reaches zero), preserving the b3 rule that a pending newer command suppresses the disconnect coordinator.py:4208-4213 because a queued ticket keeps the count nonzero. The transport-operation gate (async_transport_operation) and diagnostics pause/resume plumbing admit as exclusive tickets, giving them the same "hold the link still" guarantee they get from the lock today.
  • Unexpected disconnect. _on_disconnect sets every active ticket's token (all motion is dead with the link on pulse protocols) and clears any intent registry; queued tickets fail fast with the existing connection error path. Reconnect/hydration scheduling is unchanged.
  • Setup / unload. async_shutdown drains: cancel all tickets, run one final child stop if any motion ticket was active (today's behavior via the cancel event, made explicit), stop any streamer, await the pump, then the existing disconnect path. Paired unload keeps b3's per-child shutdown gather paired_coordinator.py:602-609.
  • Child availability. Unchanged: entities stay always-available entity.py:32-41; a disconnected side fails at connect time inside its own ticket; snapshot-driven capabilities untouched. Half-available pair setup (paired_coordinator.py:551-594) untouched.

class CommandKind(StrEnum):
    MOTION = "motion"; PRESET = "preset"; AUX = "aux"; QUERY = "query"; STOP = "stop"

class CommandLifetime(StrEnum):
    DURABLE = "durable"; RELEASE_BOUND = "release_bound"

class CompletionPolicy(StrEnum):
    OPERATION_RETURN = "operation_return"; POSITION_FEEDBACK = "position_feedback"
    PROTOCOL_NOTIFICATION = "protocol_notification"; DEADLINE = "deadline"

@dataclass(frozen=True, slots=True)
class CommandScope:
    kind: CommandKind
    axes: frozenset[str] = frozenset()      # "back", "legs", "left:back", ...
    aux_channel: str | None = None          # "lights", "massage", "firmness"
    exclusive: bool = False                 # presets, transport ops, legacy default

    def conflicts_with(self, other: CommandScope) -> bool: ...

LEGACY_EXCLUSIVE = CommandScope(kind=CommandKind.MOTION, exclusive=True)

@dataclass(slots=True)
class CommandTicket:
    ticket_id: int
    scope: CommandScope
    lifetime: CommandLifetime
    completion: CompletionPolicy
    owner_id: str | None                    # pointer/key owner for RELEASE_BOUND work
    cancel: asyncio.Event                   # what coordinator.cancel_command resolves to
    stop_generation: int                   # snapshot, rechecked immediately before activation
    admitted_at: float
    deadline: float | None                  # the op's own timeout (e.g. seek 60 s)
    pulse_override: tuple[int, int] | None  # timed_move, replaces field mutation
    state: TicketState                      # QUEUED | RESERVING | RUNNING | DONE | ...

class WireGate:
    async def step(self, ticket: CommandTicket) -> AsyncIterator[None]: ...  # ctx manager, one atomic step
    def stop_pending(self) -> bool: ...

class ChildCommandScheduler:
    def __init__(self, profile_fn: Callable[[], MotionConcurrencyProfile]) -> None: ...
    async def run(self, scope: CommandScope,
                  op: Callable[[CommandTicket], Coroutine[Any, Any, T]],
                  *, replace_conflicting: bool = True) -> T: ...
    def request_cancel(self, scope: CommandScope) -> None: ...   # scoped; ALL via exclusive scope
    async def run_stop(self, op: Coroutine[Any, Any, None]) -> None: ...  # priority, always completes
    def release_scope(self, scope: CommandScope) -> None: ...    # hold release: drop queued,
                                                                 # cancel-and-stop only if active
    async def reserve(self, ticket: CommandTicket) -> Reservation: ...
    async def activate(self, reservation: Reservation) -> None: ...
    def on_idle(self, cb: Callable[[], None]) -> Callable[[], None]: ...
    @property
    def active_scopes(self) -> tuple[CommandScope, ...]: ...     # diagnostics + pair router

    def clear_intent(self, ticket: CommandTicket, axis: str) -> None: ...

12. Diagnostics

  • record_command_trace entries gain ticket_id, scope, lifetime, completion_policy, queued_ms, and terminal outcome (completed / replaced_by / stopped / timed_out / disconnected / dropped_on_release).
  • New scheduler section in the diagnostics payload per child: concurrency profile (model + evidence string), active tickets with age and state, queue depth and per-ticket queue age, last 20 admission decisions (admitted / replaced X / queued behind Y / coalesced with Z / dropped stale).
  • Pair diagnostics add route (pass_through / two_phase / sequential), group ID, reservation state per physical identity, blocker ticket, and resolved connection mode.

13. Focused tests

  1. Scope algebra unit tests: conflict matrix, replacement, queue-not-cancel for disjoint scopes, stale-queued drop, same-scope coalescing, exclusive vs axis vs aux vs query, side-prefixed axes.
  2. WireGate: STOP overtakes FIFO; step atomicity (a burst is never split); idle callback fires only at zero active and queued tickets; queued-wait warning emitted at threshold without failing the ticket.
  3. Seek interruption matrix (time-virtualized clock, recording controller double asserting ordered writes, per the repo's anti-self-fulfilling-mock rule): under the default SERIAL profile, a cross-axis command mid-seek produces zero writes until the seek's final stop, then runs to completion, and the seek reaches its target; under a declared DEAD_MAN_INTERLEAVE fixture profile, the same command's burst lands only at a yield boundary and never splits a seek burst; same-axis command replaces; STOP halts with final stop write; disconnect mid-seek cancels the ticket and skips further writes.
  4. Legacy identity: replay the b3 command sequences through unannotated call sites and assert wire-trace byte identity, including cancel timing (a second exclusive command still preempts the first mid-burst).
  5. Pair routing: separate-address concurrent mode overlaps independent child activity while each child trace stays serial; a linked both group reserves in canonical operation_identity order and neither child writes until every reservation is READY; cancellation during reservation writes nothing; failure after activation still stops every possibly-started side; Octo sequential tests remain byte-identical.
  6. Hold release scoping: release of a hold whose ticket is still queued emits no wire traffic, drops the ticket, and leaves the concurrent-axis seek running; release of an active hold cancels it and writes the stop; bed-wide Stop button still stops everything.
  7. Composite target service: all targets preflight before admission; single-address targets deduplicate by operation_identity; SERIAL ordering is deterministic; group cancellation prevents unstarted targets; result attributes errors to target and side.
  8. Direct-target tracking: without coexistence evidence the seek ticket stays active until feedback reaches tolerance or timeout, and a second-axis request queues behind it; with a coexistence fixture profile the ticket completes at write time and both writes land back-to-back.
  9. Evidence enforcement: a unit test walks every registered controller and fails if motion_concurrency.model != SERIAL with an empty evidence string.
  10. Combined-frame streamer (lands with M4): single intent frame bytes identical to today's single-axis command; union frame asserted against the declared builder; last-intent-removed emits release; STOP clears registry then writes stop_all.
  11. Lifecycle: disconnect-after-command fires only when active and queued counts reach zero; idle timer not re-armed while tickets are queued; shutdown drains queue and sends final stop when motion was active; unload during an active barrier stops both sides.

15. Rejected alternatives

  • "Safe by construction" burst interleaving. Rejected because byte similarity does not prove timing or firmware session behavior. No unverified protocol receives alternating motor bursts. SERIAL queue-not-cancel is the default; DEAD_MAN_INTERLEAVE requires evidence.
  • A map of per-axis asyncio locks. No model for exclusive presets or aux/query lanes, deadlock-prone for multi-axis operations, no stop priority, no replacement semantics. Scopes + one gate express all of it.
  • Keep the global lock, only scope the cancellation. Nearly M1, but without the queue model there is no coalescing, no queue visibility, no idle accounting for disconnect-after-command, and the seek still monopolizes the lock against QUERY reads. The scheduler gives the same safety with an honest queue.
  • Run seeks as detached background tasks outside the lock. Loses the STOP ordering guarantee (a stop could land between a detached task's writes with no ordering), races the disconnect path, and breaks the disconnect-after-command accounting. The scheduler keeps long ops inside the ordered world.
  • Put the scheduler in the pair parent. The parent has no BleakClient and single beds have no parent; scheduling would need a synthetic parent everywhere, violating b3's composition-over-rewrite invariant and re-deriving the reconnect-storm-sensitive child lifecycle.
  • Per-axis command characteristics / one BleakClient per axis. No protocol in the tree exposes independent per-axis GATT endpoints, and a second client per device breaks the one-link invariants and adapter slot budgeting.
  • Optimistic simultaneity with runtime probing. Probing means moving a user's bed to find out what their firmware does. Violates the no-guessing rule; declarations with evidence are the only acceptable source.
  • Frontend-side fan-out or client-side queueing. The card must never own safety semantics (existing rule for paired both; same reasoning here).

17. Evidence rules and open hardware questions

What counts as authoritative evidence for any non-SERIAL declaration, per the repository's standing rules:

  • A fresh APK decompile (jadx/blutter) of the vendor app showing the app itself emitting the claimed pattern, cited by artifact path and finding. Legacy protocol writeups are diff-baseline only and never qualify on their own.
  • Vendor protocol documentation for the specific module.
  • A dated bench test on real hardware, recording bed model, module, firmware where visible, and the exact wire trace exercised.

Analogy to a sibling protocol, b3 happening to permit a byte sequence, or "it should be fine" reasoning about timing are explicitly not evidence. The questions below block declarations (M3 to M5); none of them blocks M1 or M2, which introduce no new wire patterns on any single link.

  1. Linak: does the control point keep both actuators moving when per-actuator run commands alternate at burst cadence, or does each write cancel the other actuator? Needs a bench test on a real Linak unit, or a decompile showing the vendor app emitting alternating actuator commands. Also: does Linak have a documented dual-actuator opcode that makes interleaving moot? (Separate question from the separate-address pair case, which needs no evidence: two Linak devices on two links already work concurrently under M2.)
  2. Keeson / Ergomotion: fresh decompile: is the motion frame a held-button bitmask, and does firmware accept a frame with two motor bits set from the app path (not just the physical remote)? What cadence does the app stream at?
  3. Reverie / Kaidi direct / BOX25: does writing a second axis target abort an in-progress firmware seek on the first axis, or do targets queue/parallelize? Does the position feedback stream stay coherent with two motors moving? Until answered per bed, direct-target seeks hold their axis scope to arrival (section 8.1).
  4. Octo: does the dead-man stream tolerate interleaved per-motor codes within one connection (does the app ever emit two motor codes in one stream when Both Up runs), and what is the minimum frame rate before a motor halts?
  5. Dead-man duty cycle generally: for each pulse protocol family, the maximum inter-burst gap before firmware halts the motor, and whether a different motor's code mid-session resets, stops, or faults the first motor. This unknown blocks any generic interleaving claim.
  6. Preset streams: for streaming recalls (BOX25 star codes, Octo preset streams), does an unrelated single write (light toggle) mid-stream abort the recall? Determines whether AUX may ever interleave into a PRESET.
