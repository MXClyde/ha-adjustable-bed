Architecture specification · v4.0.0b3 baseline

Scoped command scheduling for every bed topology

Unrelated commands must stop cancelling one another. The universal behavior is safe ordering. Physical overlap is enabled only when the topology or protocol proves it can support it.

01 · Decision

Schedule per physical command channel

Keep v4's coordinator topology. Add one DeviceCommandScheduler for every distinct operation_identity. Convert PairedBedCoordinator from a long-held pair lock into a topology router and linked-group coordinator.

All protocols

Same resource replaces. Different resource queues. STOP preempts. No queued movement survives caller cancellation, release, disconnect, unload, or restart.

Separate physical links

Independent schedulers run concurrently when the existing v4 connection mode permits both links. Each device still receives a serial wire trace.

One physical link

Only a protocol-owned execution strategy may combine, interleave, or overlap resources. Unknown protocols remain serial.

User-visible contract: sending legs while back is moving never cancels back merely because it is a different resource. On an unverified bed, legs waits. On a verified capable bed, both may progress.

03 · Safety invariants

Rules no strategy may weaken

InvariantRequired behavior
One physical transport ownerOne scheduler exists per distinct BLE command channel. The controller's existing BLE lock continues to serialize individual GATT operations.
No guessed timingUnknown controllers receive one complete legacy operation at a time. Generic scheduler code never alternates frames or slices opaque controller coroutines.
No stale motionA queued command cannot start after its caller is cancelled, a hold is released, STOP lands, the link disconnects, the entry unloads, or Home Assistant restarts.
Cleanup before replacementSame-resource replacement sets only that ticket's token, waits for its protocol cleanup, then starts the newer intent.
STOP always winsSTOP invalidates covered active and queued work before waiting for the current GATT operation, attempts every required target, and never returns early because a newer request appeared.
Physical completion is modeledA successful write is not assumed to mean movement finished. The execution strategy owns the completion signal and motion lease.

Existing query evidence onlyPosition reads already issued inside b3 movement may remain there. External queries and auxiliary writes queue unless the specific strategy proves safe admission.
No reconnect replayDisconnect fails active and queued movement. Reconnect hydrates state only; it never resumes an earlier command.
No user safety toggleConcurrency capability is integration-owned, controller-specific, variant-aware, and evidence-backed.
04 · Structure

Routing, scheduling, strategy, transport

Keep public coordinator shapes

Existing entities and services still call coordinator entry points. Compatibility wrappers create a default intent around the existing controller coroutine. Migration can be incremental.

Do not put scheduling in BLE transport

The transport owns connection and GATT safety. It should not know motors, sides, presets, replacement, or user intent.

05 · Command model

Intent owns meaning; context owns execution

@dataclass(frozen=True, slots=True)
class CommandIntent:
    intent_id: str
    group_id: str | None
    resources: frozenset[ResourceKey]       # physical identity + logical side + axis/group
    kind: CommandKind                      # MOTION, PRESET, AUX, QUERY, MAINTENANCE
    lifetime: IntentLifetime               # ONE_SHOT or HELD
    replacement_key: ReplacementKey
    completion: CompletionPolicy
    operation: ControllerOperation         # opaque legacy coroutine or strategy-native plan

@dataclass(slots=True)
class CommandContext:
    cancel_event: asyncio.Event
    admission_stop_epoch: int
    pulse_override: PulseSettings | None
    caller_alive: Callable[[], bool]
    hold_owner: HoldOwner | None

class CommandHandle:
    state: QUEUED | PREPARED | ACTIVE | CLEANING | TERMINAL
    outcome: COMPLETED | REPLACED | RELEASED | STOPPED | CANCELLED | FAILED

ONE_SHOT

A target, preset, or timed move stays valid while its service or entity call is alive. If that caller is cancelled before activation, the queued intent drops. It is never persistent across unload, disconnect, or restart.

HELD

A live input has a stable owner ID and generation. Release or card teardown invalidates the owner. Queued work drops with zero BLE traffic; active work follows strategy cleanup.

Compatibility context

Existing controller movement methods do not accept a command context. During migration, the scheduler binds CommandContext through task-local context so coordinator.cancel_command and pulse-setting accessors resolve to the active ticket. New strategy-native code receives context explicitly. Controller-created background tasks must be audited because task-local context is copied when a task is created.

Important simplification: resource groups such as a preset, native both command, or stop-all are intent scopes, not separate execution strategies. This avoids multiplying strategy types for commands that merely own more resources.
06 · Scheduler contract

Small policy, explicit state

The default scheduler is a resource-aware FIFO. It does not attempt general fairness classes or deadline optimization. Safety actions are the only priority exception.

Incoming eventScheduler actionWire consequence
Same replacement keyInvalidate older queued intents; cancel the active matching ticket; wait for CLEANING; activate newest if still live.Required cleanup separates old and new operations.
Different resource, serial strategyAppend FIFO without touching the active ticket.Current operation completes, then the new operation runs unchanged.
Different resource, capable strategyAsk the strategy whether the exact resource set is admissible.Strategy may combine, interleave, or issue independent targets.
HELD owner released while queuedMark RELEASED and remove every queued renewal for that owner.No movement and no STOP write.
HELD owner released while activeSet its ticket token and invoke strategy resource release.Serial strategy uses existing cleanup; richer strategies preserve other resources only when proven.
Caller cancelledDrop queued ONE_SHOT or cancel active ticket and finish cleanup.No delayed action after caller disappearance.
STOPIncrement stop epoch synchronously; invalidate covered queues and active tokens; enter safety lane.After current atomic GATT operation, send the required STOP or release to every target.
Disconnect or unloadFail active and queued tickets, invalidate owners, clear strategy intent state.No replay after reconnect.

Stop epoch closes the admission race

Every ticket snapshots the device's monotonic stop epoch on admission and rechecks it immediately before activation. STOP increments the epoch before awaiting anything. A movement admitted just before or during STOP therefore cannot start after the safety command.

Held renewals do not become a backlog

At most one queued renewal exists per held owner and replacement key. A later renewal coalesces into it. A durable position target may replace an older target for the same axis, but never silently merges with another axis.

Opaque commands remain opaque

SerialOpaqueStrategy holds the device execution lane for the whole existing command or seek. The scheduler does not release the lane during arbitrary sleeps and does not insert auxiliary writes between controller frames. That universal path fixes cross-resource cancellation by ordering, without changing protocol timing.

07 · v4 topology and groups

One router, three physical realities

TopologyRouting behaviorConcurrency result
Separate addresses, concurrent modeSingle-side work passes directly to that child scheduler. Linked both work is prepared on both schedulers, then committed as a group.Left and right may overlap. Each child remains serial unless its own strategy proves more.
Separate addresses, sequential modeKeep b3's parent connection lane and connect, operate, disconnect order. The lane is the reservation.Never more than one link. Other-side work queues. No generic time slicing.
Single addressDeduplicate by operation_identity and submit one multi-resource intent to the shared scheduler. Use native both routing where b3 already does.One physical lane. Same-link overlap requires that controller's strategy.

Linked prepare and commit

  1. Preflight every logical target before admission, preserving b3's all-target validation.
  2. Under a short pair metadata mutex, synchronously enqueue one GroupMember per distinct physical identity. This mutex is never held across connect, controller, sleep, or GATT work.
  3. A member becomes READY when its scheduler can activate it without violating its local strategy. READY does not execute controller code.
  4. When every member is READY, the router commits the group and starts all concurrent-mode members. If cancellation or failure occurs before commit, every member releases with zero movement.
  5. After commit, first failure cancels the linked group, attempts cleanup on every member that may have started, and raises side-attributed errors including cleanup failures.
Why prepare/commit matters: merely acquiring left before right can let one side move while the other is still queued. Queue entries plus an explicit commit point preserve the b3 whole-bed intent without holding a global operation lock.

Independent requests stay independent

A left-only request and a separately issued right-only request do not become one failure group. Failure on one does not stop the other. Safety coupling exists only when the caller submitted a linked both or composite group.

Strategy interface

class ProtocolExecutionStrategy(Protocol):
    profile: ExecutionProfile

    def can_admit(self, active: ActiveIntentSet, incoming: CommandIntent) -> bool: ...
    async def execute(self, intent: CommandIntent, context: CommandContext) -> None: ...
    async def release(self, intent: CommandIntent, context: CommandContext) -> None: ...
    async def stop(self, resources: frozenset[ResourceKey]) -> None: ...
    def completion(self, intent: CommandIntent) -> CompletionPolicy: ...

@dataclass(frozen=True, slots=True)
class ExecutionProfile:
    strategy: StrategyKind = StrategyKind.SERIAL_OPAQUE
    admissible_resource_sets: tuple[frozenset[str], ...] = ()
    stop_scope: StopScope = StopScope.DEVICE
    evidence: EvidenceRecord | None = None

Evidence gate

  • Any non-default profile must name the exact controller and variant and carry structured evidence metadata.
  • Accepted evidence is a clean-room vendor-app analysis showing the claimed path, vendor protocol documentation, or a dated hardware trace with model and firmware where available.
  • APK work must follow the repository's Phase 4 clean-room workflow and frozen-report gates. Existing historical notes are comparison material, not proof by themselves.
  • Tests fail registration when a non-default profile has no evidence or lacks the fields its strategy requires.
  • User configuration cannot override the resolved profile.
Not evidence: a controller has two motor methods, a packet contains several fields, direct-position control exists, another brand looks similar, or the current lock happens to prevent a combination from being tested.
09 · STOP, connection, completion

Scheduler state owns lifecycle boundaries

Connection lease

Queueing alone does not seize a BLE link. Activation ensures connection and auth. If a successor is already ready, keep the connection as b3 does for a pending newer command; otherwise apply disconnect-after-command or reset the idle timer.

Motion lease

Tracks physical movement beyond a short write. Serial admission and disconnect decisions use the lease, not coroutine return. The strategy ends it from feedback, notification, release, STOP, timeout, or disconnect.

Maintenance lease

Diagnostics, transport operations, and hydration that require exclusive connection state enter as maintenance intents. They do not bypass movement ordering.

STOP scopes

ActionScopeRule
Visible Stop button / stop_allChild, side, or pairKeep b3's safety meaning. Drain covered queues and attempt all targets even if one fails.
Same-axis replacementMatching resource or linked groupCancel matching ticket. If it belongs to an active linked group, cancel the whole group to avoid desynchronization.
HELD release on SerialOpaqueQueued owner or sole active motionDrop queued with no write. If active, use existing protocol cleanup; serial execution ensures there is no unrelated simultaneous motion to preserve.
HELD release on richer strategyDeclared resource scopeStrategy must prove how to remove one resource while preserving others. Otherwise multi-hold is not exposed.
Silence-only protocolRefresh ownershipEnd the proven held-command refresh. Do not invent a STOP frame.

Fault outcomes

Unexpected disconnect cancels active operations, fails queued intents, clears combined state, and marks completion uncertain where STOP could not be confirmed. Setup shutdown does the same before existing disconnect cleanup. Diagnostics record whether cleanup was attempted, confirmed, failed, or impossible because the link was gone.

10 · Services, entities, frontend

Backend owns grouping and truth

Existing calls

Keep existing entities and services. Each becomes a one-intent wrapper with an explicit resource and replacement key. No config migration.

Composite targets

Add one set_positions service after group scheduling is stable. Preflight every target, then submit one group. The strategy decides ordered or overlapping execution.

Frontend truth

Replace browser-side sequential synchronization with the composite service. Show queued state only from backend diagnostics or response state. Never optimistically claim movement.

adjustable_bed.set_positions
device_id: paired-bed
targets:
  - { side: right, motor: back, position: 42 }
  - { side: right, motor: legs, position: 18 }

# All-target preflight. One group result.
# SerialOpaque runs these in order; a verified strategy may overlap them.

Held controls

The current card remains single-hold until a backend held-intent API exists. That API gives start/renew/release calls one stable owner ID, moves pulse renewal into the scheduler, and lets release invalidate queued work. Resource-keyed multi-pointer UI is enabled only when the resolved profile can make progress on the requested resources and release them safely.

Diagnostics, not entity spam

Add bounded command-trace fields: intent ID, group ID, operation identity, resources, strategy, state, queue age, active age, blocker, stop epoch, completion policy, cleanup outcome, and terminal reason. Do not add one Home Assistant entity per queue or ticket.

Release acceptance

  • Full existing suite passes, plus focused scheduler, group, lifecycle, and frontend tests.

  • Any enabled non-default strategy has evidence metadata and protocol-specific tests.
13 · Rejected shortcuts and non-goals

What this architecture deliberately avoids

Rejected

  • Per-axis locks without a group, STOP, completion, or lifecycle model.
  • asyncio.gather on one controller and one BLE link.
  • Generic slicing of controller coroutines at sleeps.
  • Assuming direct targets, combined fields, or similar brands imply concurrency.
  • Runtime probing that moves a user's bed to discover behavior.
  • Frontend-owned queues, fan-out, retries, or partial-failure cleanup.
  • Replaying movement after reconnect.

Not required for the root fix

  • Simultaneous motion on every bed.
  • A user-selectable scheduling profile.
  • New queue entities in Home Assistant.
  • Rewriting every controller before the scheduler lands.
  • Fairness algorithms beyond safety ordering and FIFO.
  • One universal STOP opcode or timing model.
  • Immediate multi-pointer UI before backend-held intent exists.
Final recommendation: land the scoped SerialOpaque scheduler first, then unlock concurrency at the two boundaries where it is actually knowable: independent physical links in v4 topology, and evidence-backed protocol execution strategies on a shared link.
